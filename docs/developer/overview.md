# 架构总览

## 分层结构

```text
            平台 QQ / OneBot / 终端
                      ↓
   ┌──────────────────────────────────┐
   │  适配器 Adapter                   │  mioku-adapter-*，对接平台
   │  ├─ 接收：平台消息 → Event        │
   │  └─ 调用：能力 → 平台指令          │
   └──────────────────────────────────┘
                      ↓
   ┌──────────────────────────────────┐
   │  命令管理器                        │  匹配、前缀、权限、优先级、帮助目录
   └──────────────────────────────────┘
                      ↓
   ┌──────────────────────────────────┐
   │  事件总线 EventBus                 │  按路由分发剩余事件
   └──────────────────────────────────┘
                      ↓
   ┌──────────────────────────────────┐
   │  插件 Plugin                      │  业务逻辑
   │  服务 Service                     │  公共能力提供方，插件取用
   └──────────────────────────────────┘
```

## 启动流程

框架启动时按以下顺序执行。

1. **发现服务**：扫描项目 `services/` 目录和 `mioku-service-*` 依赖，加载全部服务。
2. **加载内置 core 插件**：注册系统命令、访问控制和状态收集。
3. **加载用户插件**：解析 `mioku.plugins` 列表，按 `priority` 分组加载。数值小的先加载，同组并行。每个插件在 `setup` 阶段注册消息命令。
4. **启动适配器**：读取 `mioku.adapters` 配置，逐个创建并启动，注册 bot 与能力。
5. **就绪**：派发 `runtime:ready` 事件。开启 `online_push` 时向主人推送上线通知。

这个顺序不是随意的。插件先于适配器加载，意味着插件在 `setup` 时可能还没有 bot 连接。依赖 bot 的初始化逻辑需要放在事件监听中，不能放在 `setup` 中。

## 四种包类型

| 包前缀 | 是什么 | 谁编写 |
| --- | --- | --- |
| `mioku-plugin-*` | 插件的功能实现 | 大多数开发者 |
| `mioku-service-*` | 跨插件复用的能力提供方 | 需要共享能力的开发者 |
| `mioku-adapter-*` | 对接平台的连接层 | 想接入新平台的开发者 |
| `mioku` | 框架本体 | 仓库维护者 |
